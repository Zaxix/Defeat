## CROSS-REFERENCED RESEARCH NOTES — 2026-11-27 (source-backed hypotheses, not instructions to port blindly)

### R20 / P0 — In-flight descriptor update hazard: a precise new hypothesis for long-run removal

- **Verified in this fork:** \`crates/victory-gpu/src/descriptor/host.rs\` method \`HostHeap::texture_views_remade\` states that live GPU-visible descriptor slots can be rewritten when \`host::submissions_in_flight() > 0\`. The code counts \`VIEWS_REMADE[1]\` ("remade while a submission was in flight"), and has an existing **opt-in** \`VICTORY_VIEWS_REMADE_QUIET=1\` mode that defers those remakes. This is a *real code-level risk candidate*, not proof it caused any of the 30–50-minute device losses.
- **Cross-reference:** Microsoft's D3D12 guidance requires applications to manage synchronization and descriptor/resource lifetimes explicitly. [Executing and synchronizing command lists](https://learn.microsoft.com/en-us/windows/win32/direct3d12/executing-and-synchronizing-command-lists), [Direct3D12 resource barriers](https://learn.microsoft.com/en-us/windows/desktop/direct3d12/using-resource-barriers-to-synchronize-resource-states-in-direct3d-12). fxceless reports intermittent \`0x887A0005\` losses despite its unrelated short-session fixes: [fork README](https://github.com/fxceless/victory-fork/blob/main/README.md).
- **Smallest decisive experiment:** retain the same branch and world scene; log \`VIEWS_REMADE[1]\`, completed/started queue submission IDs, descriptor slot, associated resource generation and DRED removal reason. Compare \`VICTORY_VIEWS_REMADE_QUIET=0\` vs \`=1\` under *separate* long runs. Note that quiet mode can delay texture updates, so compare screenshots and blank slots too. Repeat with D3D12 debug/GPU validation separately; those modes themselves affect timing. A disappearance of crashes in one run is not sufficient proof; repeat.
- **If confirmed — design hypothesis:** do not mutate a descriptor slot that any queued/in-flight list may still read. Version the host descriptor allocation per in-flight use (or defer a slot's rewrite until its **last referencing queue fence** completes); retain the previous resource and descriptor until the same fence. A global idle wait is a correctness control, not necessarily a performant final design. Prove that old and new descriptors never alias in a live list, and validate zero stale-resource reads.
- **Related separate check:** fxceless [commit \`2ba6e1f\`](https://github.com/fxceless/victory-fork/commit/2ba6e1f99844e3765d66e7710e02e541daa0f9b4) caps CBVs at the host's 64 KiB limit after an NVIDIA \`CreateConstantBufferView\` invalid-call report. **Do not assume this is absent or present in the target branch**: inspect \`constant_view_size\`/CBV creation and already-existing capped-descriptor code before acting. Distinguish CBV-invalid-call failures from descriptor-in-flight races and from the main heap-slot cap fix.
- **Crash evidence to collect:** reason (\`DXGI_ERROR_DEVICE_REMOVED\`, \`DEVICE_HUNG\` or \`INVALID_CALL\`), DRED breadcrumbs/page-fault result, last complete submission, allocation names/IDs, descriptor slot writes, live resource/heap counts, driver/event log, VRAM budget, and time-to-failure. No reported page fault does **not** exonerate invalid GPU commands or synchronization bugs. Microsoft's [DRED spec](https://microsoft.github.io/DirectX-Specs/d3d/DeviceRemovedExtendedData.html) explains limitations. If the specific fork supports \`VICTORY_D3D12_DRED=faults|light\`, \`faults\` captures page-fault information with less tracing and \`light\` includes breadcrumbs (fxceless [\`4cc775f\`](https://github.com/fxceless/victory-fork/commit/4cc775f57839907a4ae932bc0a9e08cd3b2e0781)); check exact branch implementation first.

- [ ] **R20 — Prove or rule out descriptor writes into live/in-flight GPU-visible slots.** Record \`VIEWS_REMADE[1]\` and consecutive long-run on/off results, plus DRED/context and screenshot correctness; if proved, require fence-based deferred rewrite/retirement tests before considering the fix complete.

### R21 / P1 — Submission thread spent on COM destruction and retirement bookkeeping

- **Verified from target fork source:** \`crates/victory-gpu/src/host.rs\` documents **36.8 million** host-object retirements across about 240 seconds in one fxceless-source test (run 313), mostly repeated descriptor writes. It already has \`VICTORY_RETIRE_LEAN=1|alt\` to avoid retiring the previous reference when the *same COM object* is retained, and \`VICTORY_REAPER=1|alt\` to move eligible destruction to another worker. This is a recorded measurement in imported code, **not a benchmark on this owner's Ryzen**.
- **Cross-reference:** \`shadow::EXACT\` [\`16183bd7\`](https://github.com/Zaxix/VIctory/commit/16183bd7c578f175beab7c076d6c5eba0346fedd) moved allocations/releases outside its lock; \`shadow::LOOSE\` [\`dc744dbb\`](https://github.com/Zaxix/VIctory/commit/dc744dbb8d5a4013176c31b324d7801e9a99cc80) similarly removes driver calls from its lock. If CPU submission is still busy after those fixes, retirement traffic is a distinct plausible remaining bottleneck.
- **Measure:** descriptor rewrites/second, same-object rewrites/second, retirement queue depth and bytes, CPU ms spent inside \`bury\`/\`reap\`/\`resource::let_go_idle\`, lock wait, highest-latency tail. Use on/off/alternating variants already present, **one flag at a time**, compare p95 frame latency and GPU completed-submission watermark. A win in lock wait alone is not enough.
- **If confirmed — design hypothesis:** replace per-retirement global-vector append/sort with a **monotonic fence-bucketed retirement queue** and batched completed-epoch draining. Drop COM objects after their *last* referencing submission completes; keep the previous object alive until then, including if a descriptor points at it. Keep destruction outside locks. Avoid "early release" merely because one copy of the pointer was replaced: another live descriptor or list may still reference it. Verify races under multithreaded recording and forced device removal.
- [ ] **R21 — Record whether retirement/object destruction actually dominates CPU submission** and compare the existing isolated flags on the owner's machine before proposing any queue rewrite.

### R13 / P2 — Fence-safe buffer recycling is **not** just a power-of-two free list

- **Verified source/review:** Belobug [PR #451](https://github.com/Belobug/VIctory-Belobug-AMD/pull/451) quarantines recycled \`shadow::exact()\` buffers, rounds to a size bucket, zeroes stale reused contents, and limits memory in the pool. An NVIDIA contributor reports an RTX 4080 test at **276 → 142 ms/frame** in one fork context (review comment on #451), not reproduced here.
- **Critical review nuance:** a reviewer states \`VICTORY_EXACT_POOL_MB=0\` does **not** reproduce the baseline algorithm (bucket rounding, two-frame eviction and host retirement are different even with pooling disabled). The same reviewer notes an interval between the submitted/queued watermark sample and descriptor-only use, where the **two-frame delay rather than proven fence ownership** protects reuse. Device tests passed on AMD GPUs; performance and the title workload were *not* tested in that review.
- **If adapting to NVIDIA:** index reuse safety by **the maximum GPU queue-fence value that can still reference the particular buffer**, plus an explicit "not yet submitted" state; don't graduate by wall-clock/frame count alone. A resource reused under the same GPU virtual address must have the required bytes reinitialized; verify all out-of-range/tail reads return zeros, including when a 64 KiB-old view becomes a shorter one. Avoid unbounded quarantine memory, and preserve the ability to retire on pressure.
- **Test plan:** create buffer A, record descriptor reference on a deferred list, evict A, allocate B with the same bucket, submit A and B in adversarial orders, then check bytes and DRED; repeat across queues, list reset, cancellation and device removal. Compare against the **true old implementation**, not just \`POOL_MB=0\`. This is a new design proposal; no claim of a tested fix.

### R07 + R08 / P1/P2 — What texture metrics **actually** count

- **Upstream counter correction:** issue [#3269](https://github.com/Marvisak/VIctory/issues/3269) reports 344–444 MB/frame as "texture uploads," but a subsequent maintainer-level code inspection in its discussion shows \`textures … MB\` includes bytes **read to hash** unchanged content even if no staging upload occurs; a synthetic WARP test read 16,384 bytes and staged **zero** on the second unchanged refresh. Do not sell the full reported number as saved PCIe bandwidth.
- **This fork already has** \`texture-digest\` [\`63b87e8\`](https://github.com/Zaxix/VIctory/commit/63b87e8ca5e26f9c20194ea576fd7d93281a25f3): XXH3-128 vs \`VICTORY_TEXTURE_DIGEST=blake3\`, with separate hashed/unchanged counters. On the Ryzen 5800X (Zen 3) a faster digest **may** reduce CPU time if texture hashing is the hot path; measure, don't assume the contributor's GB/s results apply.
- **Remap correctness:** upstream [#916](https://github.com/Marvisak/VIctory/issues/916) found a \`title_memory_remapped\` / \`UnmapViewOfFile2\` ordering race in an *epoch-cached* design, fixed there by notifying after unmap. **Do not copy that epoch fix blindly**: Claude's \`texture-digest\` commit explicitly says this fork does not cache the mapping epoch and instead uses mapping guards. Its specific race/correctness tests still need actual Windows execution.
- **If hashing remains dominant — next idea (hypothesis):** only cache a per-subresource digest with a **memory-map generation/epoch that is updated after completed remapping**, and do not skip the underlying read for untracked/possibly-DMA-written memory. First prototype separate counters for unchanged/changed, remap misses, digest CPU ms, actual detile and upload bytes. Partial detiling [#915](https://github.com/Marvisak/VIctory/issues/915) makes sense only if the dirty set is exact and page-to-tile overlap is correct. Tests: stable virtual address remapped to different physical backing, streaming mips appearing late, tail-byte mutation, concurrent unmap, failed upload retry. This is **not** an adaptive memory manager.

### R14 / P2 — Ray tracing has a new *working but much slower* implementation path

- **Verified public commit and source:** fxceless [\`9a9091d\`](https://github.com/fxceless/victory-fork/commit/9a9091d180f044726463d3db819808086daeebae), 2026-11-27. It restricts each list's memory synchronization to the copies its dispatches reference, records **64 KiB GPU-written pages** instead of treating every remembered buffer as written, and reads a ray-structure SRV address from \`RaytracingAccelerationStructure.Location\` instead of defaulting to zero. It also adjusts instance/procedural node return semantics. Reported result: previous builder null write was the **title's 30-second watchdog** because no frame completed; after fixes shadows and bounce light appear but execution falls to **0.2–3 FPS**, with about **8 GB of host-copy synchronization per frame** in that contributor's trace.
- **Critical source warning:** \`memory.rs\` admits a list may miss a copy reached only through an indirect pointer from another list; \`Shadow::pull_back\` admits that a title CPU write made after the GPU write can be overwritten because the destination was not snapshotted. This is not yet a correctness-complete cross-platform memory protocol. Its local tests and reports do not establish correctness on your fork or your Ryzen PC.
- **Proposed test-first improvement:** trace a **per-submission list of guest memory ranges actually accessed**, and distinguish read, write, pointer-chased unknown and unmapped. For uncertain pointer-chased access, conservatively retain the old path. For proven writes, track 64 KiB dirty pages only; copy them back **after the producing queue fence** and protect against CPU writes with a per-range version or pre-image comparison (or serialize the overlapping ownership). Before moving work off the frame path, prove the texture/readback/RT results match a strict baseline. Do not pretend the observed BVH node format alone is native PC DXR, and do not borrow a game-specific offset without validating the binary SHA.
- **Cross-reference:** the experiment is compatible with *researching* the GPU access-flag counters in Zaxix branch \`gpu-access-costs\`, but that module says it **does not currently skip any work** and cannot observe every \`VirtualFree\`; never turn a read-only flag into an unchecked no-copy shortcut. The owner's **adaptive memory manager stays deferred**.
- **Priority rationale:** ray-traced output is valuable, but a path at 0.2–3 FPS is not an unconditional replacement for a stable, faster build.

## P1/P2 — Adaptive memory placement (owner reactivated 2026-11-27)

### R35 — DirectStorage scratch RAM and existing Windows counters (research addendum, 2026-11-27)

- **New R30 scratch is a measurable RAM owner, not a hypothetical optimisation:** [`dstorage.rs`](../crates/victory-hle/src/modules/dstorage.rs#L998-L1056) keeps up to **16 MiB per buffer** (default `VICTORY_DSTORAGE_SCRATCH_MB=16`) across four buffers for **each** storage worker; with 16 default workers on the 5800X the **theoretical maximum retained capacity is 4 × 16 × 16 MiB = 1 GiB**. This is not measured consumption or residency; allocations grow with request size and >limit buffers are dropped after each request. BC6/BC7 symbol records use **2× decoded output bytes**, so >8 MiB outputs can exceed a 16 MiB per-vector retention cap.
